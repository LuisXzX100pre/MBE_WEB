## Setup
Use existing PostgreSQL/Supabase DATABASE_URL and DIRECT_URL configuration. Never point development migration commands at production. JWT_SECRET (minimum 32 characters) is required by the existing authentication system. Existing application credentials, including STRIPE_SECRET_KEY, remain unchanged.

Community media uses Vercel OIDC with @vercel/blob pinned to 2.5.0 and the existing PRIVATE store mbe-community in the same Vercel project. BLOB_STORE_ID must contain that store's actual ID (not its display name); both store_<id> and <id> are accepted. Vercel supplies VERCEL_OIDC_TOKEN automatically in production. In local development, link this checkout to the correct project with npx vercel link if needed, then run npx vercel env pull .env.local and restart npm run dev. This pulls BLOB_STORE_ID and the short-lived VERCEL_OIDC_TOKEN. Pull again if local credentials are missing or cannot be refreshed. Never expose these variables with NEXT_PUBLIC_. Keep the existing BLOB_READ_WRITE_TOKEN and public product store untouched. Community resolves/refreshes OIDC using @vercel/oidc (installed by the Blob SDK) and returns 503 if OIDC or the store ID is unavailable; it never falls back to the product credential. Files upload directly to Blob, bypassing serverless body limits. Image maximum is 10 MB; video maximum is 50 MB. Allowed MIME types: JPEG, PNG, WEBP, GIF, MP4, WEBM. The Community client uses uploadPresigned(); its ADMIN-only route uses issueSignedToken() and presignUrl() because legacy handleUpload() in 2.5.0 still requires a read-write token. Signed upload permissions allow only put at the validated community/ pathname, expire in ten minutes, enforce MIME and size, add a random suffix, and cannot overwrite blobs. Access remains private. No upload-completed webhook or BLOB_WEBHOOK_PUBLIC_KEY is required. Post creation verifies ownership, MIME and size through Blob head(). Published media is streamed through a membership-protected authenticated route, including HTTP range requests. Unpublished media is readable only by ADMIN. Do not use a public store for exclusive media.

Deleting a post removes its comments through the foreign key. Blob files are retained so editing/reused files cannot be accidentally destroyed; orphan asset cleanup is a separate maintenance task. Uploaded assets are not inserted in PostgreSQL as binary data.

## Behavior
/comunidad requires the existing token session; anonymous visitors go to /login?next=/comunidad. Login accepts only /comunidad and /comunidad/acceso with a validated code query, preventing open redirects. Every private Community API checks the user in PostgreSQL through getCurrentUser and requires CommunityMembership. The redemption endpoint requires a session but intentionally allows nonmembers. Every admin handler independently requires ADMIN. Mutations also reject cross-origin requests.

Posts are newest-first with cursor pagination. Comments use plain text (no HTML), length 1?1000, username and dates; the server requires a published post. A serializable transaction enforces at most five comments per minute. A conflicting comment request returns 409 and can be retried. Community feed pages load 12 posts and 20 comments at a time. Images are lazy loaded; videos use controls, preload=none and no autoplay.

The wheel accepts no client userId, campaignId or prize. Server crypto.randomInt selects from the campaign-configured weights for 2/4/5/10 values. @@unique([userId, campaignId]) plus serializable transactions and conflict retries protect against repeated/concurrent requests. Existing spins are returned without another draw. Current campaign = the ADMIN-selected active campaign whose dates contain now. Activating one deactivates all others in a Serializable transaction; start is inclusive and end exclusive. Historical overlaps, if present, resolve by createdAt DESC then id DESC until the next activation. Results remain stored historically; the UI shows the current campaign result or the latest previous result when no campaign is open. usedAt is prepared but no checkout integration exists.

Events support active/future listings. Only admins assign tickets to an existing exact username. Codes use 80 bits of random data plus a unique DB index. Discounts are integer 1?100; expiry defaults to event end and cannot exceed it. Used timestamps cannot be reset or overwritten by repeated admin actions. Tickets are visible only to the recipient or ADMIN. Admin lists show bounded latest records (100 posts/campaigns/events, 200 comments/tickets, 500 campaign spins).

No Stripe, checkout, inventory, shipping or existing order logic is changed.

## Acceso exclusivo e invitaciones
Una cuenta User permite utilizar la tienda y no concede acceso a Comunidad. CommunityMembership es la fuente de verdad del acceso persistente; no depende de un invite obligatorio. El contador Home sigue contando esas membresías. Una visita, un GET o un registro normal jamás crean una membresía. Los registros de membresía anteriores se conservan: algunos pudieron originarse en el antiguo registro de visitas. Esta migración no los reclasifica ni revoca; revisar esos miembros requiere una decisión separada del propietario.

Flujo: /comunidad sin sesión -> /login?next=/comunidad; sesión sin membresía -> /comunidad/acceso; miembro -> contenido. /comunidad/acceso redirige a miembros hacia /comunidad. Los ADMIN pueden preparar invitaciones y gestionar Comunidad sin ser miembros, pero para ver contenido, medios, ruleta y eventos mediante las rutas de miembros también necesitan CommunityMembership. Las APIs privadas verifican membresía en servidor, además de sesión; nunca basta el JWT del navegador. No se cambia middleware ni el sistema JWT. Login permite únicamente los destinos locales exactos de Comunidad y su ruta de acceso con un código validado.

CommunityInvite admite INDIVIDUAL (maxUses=1) o CAMPAIGN (1–10000 usos finitos). active permite pausar; expiresAt=null no expira, y una fecha <=ahora rechaza el canje. Usos y expiración se evalúan en servidor. Editar conserva tipo, hash e ID, y no permite reducir maxUses por debajo de uses. Un código automático utiliza crypto.randomBytes(16), 128 bits de entropía, con formato MBE-XXXXXXXX-XXXXXXXX-XXXXXXXX-XXXXXXXX. Los personalizados admiten 8–64 caracteres ASCII A–Z, 0–9 y guiones; se normalizan con trim+uppercase. No hay códigos ilimitados.

Solo codeHash se persiste: HMAC-SHA-256 con una clave derivada de JWT_SECRET usando el dominio mbe-community-invite-v1. No se añade un secreto. JWT_SECRET debe ser el mismo existente en los entornos apropiados, con mínimo 32 caracteres. Rotarlo invalida los hashes de invitaciones anteriores, además del efecto existente sobre sesiones: preparar nuevos códigos al rotar. El servidor busca por hash; nunca compara plaintext guardado. Las etiquetas tampoco admiten el código completo incrustado. Tras crear, el código aparece una sola vez en la respuesta/pantalla ADMIN con Cache-Control private,no-store; debe copiarse entonces. Listados, edición e historial no devuelven hash ni plaintext. No se guarda el código en localStorage, logs ni BD.

POST /api/community/access/redeem obtiene userId exclusivamente de la sesión y solo acepta code. Código inexistente, inválido, inactivo, vencido o agotado produce el mismo mensaje: Código inválido o no disponible. El canje usa transacción Serializable con hasta cinco intentos ante P2034; una actualización condicionada incrementa uses solamente si active, expiración y límite siguen siendo válidos. Uso, membresía y redención se confirman juntos o se revierten juntos. Un CHECK de PostgreSQL exige 0<=uses<=maxUses, maxUses entre 1 y 10000 e individuales de un uso. UNIQUE de CommunityMembership.userId y CommunityInviteRedemption.userId impiden dobles concesiones/redenciones. Un miembro ya existente obtiene respuesta idempotente sin gastar usos ni nuevos intentos. Desactivar, agotar o vencer una invitación impide nuevos canjes; no revoca membresías ya concedidas.

El rate limit permite cinco intentos por usuario en una ventana móvil de diez minutos. CommunityAccessAttempt persiste únicamente userId y fecha, sin código ni hash. Una transacción Serializable cuenta y registra cada intento; se confirma antes del canje, por lo que un código incorrecto no borra el intento. Se eliminan intentos viejos de ese usuario al siguiente intento. Los datos de usuarios que nunca reintentan pueden conservar registros viejos; su limpieza global queda para mantenimiento. El sexto intento recibe 429. Esto funciona entre instancias serverless y no usa memoria ni Redis. Un conflicto que exceda los reintentos devuelve 409 y permite reintentar sin acceso concedido parcialmente.

/admin/comunidad -> Accesos permite crear, editar nombre/límite/expiración, activar/desactivar, ver ACTIVO/AGOTADO/EXPIRADO/INACTIVO y consultar usos. Los listados e historiales paginan de 50 en 50. El historial solo muestra username y fecha; no passwords, email ni tokens. Una invitación usada no puede eliminarse: se desactiva. Las foreign keys RESTRICT conservan la trazabilidad y protegen carreras de eliminación/canje. Borrar usuarios con redenciones también queda restringido para conservar el historial.

/comunidad/acceso?code=XXXX prellena exclusivamente el formulario; nunca canjea mediante GET. La confirmación siempre es POST. El retorno de login conserva este parámetro seguro. Así queda preparada la entrada por links o futuros QR, sin generar imágenes QR ahora. Una compra, evento o concesión manual podrá crear CommunityMembership en una fase futura sin invitar ni cambiar este modelo; no se conecta ninguna lógica de compra en esta fase.

## Campaña y ruleta — feat/community-campaign-wheel
Se reutiliza CommunityWheelCampaign; no existe otro sistema de campañas. name es interno; title, subtitle, description y note controlan el copy visible. La sección de campaña/ruleta aparece antes del archivo y eventos. Los datos iniciales se cargan en servidor después de verificar CommunityMembership. Sin campaña vigente se muestra un estado de espera, sin botón de giro, y se conserva el último resultado histórico. Durante una campaña actual se muestra el resultado de esa campaña; un miembro puede obtener un nuevo giro en una campaña diferente.

Activa = seleccionada por ADMIN, inicio null o <=ahora, fin null o >ahora. Activar una campaña desactiva las demás dentro de una transacción Serializable con hasta cinco intentos ante P2034. Activar una campaña futura reemplaza inmediatamente la selección anterior: habrá estado de espera hasta que empiece. La selección compartida de GET/POST usa el mismo filtro y desempate (createdAt,id descendentes) para datos históricos solapados. No se actualizan datos históricos mediante la migración. Estos criterios se aplican en servidor, independientemente del reloj del navegador.

Admin -> Campañas / ruleta permite crear, editar copy, vigencia y nota, activar/desactivar y consultar giros. Se mantienen los premios 2%, 4%, 5%, 10% y su restricción SQL existente. prizeWeights guarda cuatro pares percent/weight; cada peso entero es 1–1000. El panel muestra probabilidades relativas; cuatro pesos 1 equivalen a 25% por opción. No se configuran premios adicionales ni descuentos enviados por el miembro. Cambiar configuración afecta exclusivamente giros futuros, nunca el resultado guardado. Las campañas anteriores con campos null conservan nombre y copy de respaldo; su configuración por defecto es la anterior, con pesos iguales.

La ruleta conserva UNIQUE(userId,campaignId), transacción Serializable y reintentos de conflicto. Un resultado existente se devuelve sin sortear ni gastar un segundo giro. El cliente bloquea doble envío, distingue «Ya participaste», muestra el porcentaje y usedAt (utilizado/sin utilizar), y refresca el estado si POST falla por cambio de campaña/vigencia. La animación se desactiva con reduced-motion. usedAt solo se lee; no se añade checkout ni mecanismo de consumo. El estado utilizado depende de los datos existentes. El navegador verifica también el fin de la campaña mientras la página está abierta; la desactivación manual se confirma al actualizar o al intentar POST, que la rechaza en servidor.

Estadísticas Admin: contador total de giros por campaña y los últimos 500 resultados, con username, fecha, porcentaje, distribución y estado utilizado. La distribución y cantidad de usados se etiquetan como correspondientes a esa lista, no como totales globales. Los listados existentes siguen limitados a las últimas 100 campañas.

Home: botón más compacto, transparente/oscuro con borde neutro; el punto rojo de presencia se mueve junto a «X personas están adentro», fuera del botón. Mantiene el conteo CommunityMembership, enlace /comunidad y prefetch=false. No cambia hero, carrusel ni lógica de acceso.
